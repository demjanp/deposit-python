# Resource-bearing imports and capacity design

**Status:** Stages 1–3 implementation and focused verification are complete. This document records the approved interface decisions and implementation contract. Stages 4–7 remain pending.

**Scope:** resource-bearing Exchange packages imported into existing Namespaces, portable package handling, graph providers, recovery, capacity and test ownership. Full-Namespace clone is included in the sequential Stage 6 implementation; its detailed contract is completed there before that stage’s implementation. Stages 1–6 execute sequentially; Stage 7 is the only full acceptance phase.

## 1. Approved interface decisions

1. **One immutable package pipeline:** select source → freeze a complete Exchange package → analyze against the target → explicit apply. Analysis never applies changes.
2. **Lazy Exchange bundles:** `Store.export_exchange(...)` returns a context-managed `ExchangeBundle`. It may initially hold a remote package reference containing source binding, resource ID, length and checksum, without claiming the manifest or graph were inspected locally. Accessing the manifest/graph/resource content, saving a portable ZIP, or converting to a graph materializes the package in protected storage and validates ZIP safety, required members, manifest integrity, checksums and lengths. Python does not duplicate Server graph/history/Pattern/scientific/geometry/time semantic validation; the Server validates those before creating an import plan or applying effects. `Store.import_from(...)` may pass the eligible remote reference directly to the target without downloading through the client.
3. **Bundle ownership:** caller-owned streams and Stores are borrowed and remain open. The bundle owns only its local protected staging. Closing a bundle releases owned staging only when no reader/workflow owns it; readers and submitted workflows pin the immutable bytes they use. Saving a portable ZIP is a separate, explicit output operation with caller-selected destination ownership. Never substitute an ordinary plaintext temporary ZIP for protected staging.
4. **Conservative routing:** direct handoff is allowed only when live endpoint/deployment provenance and database identity are sufficiently certain and the receiving actor is authorized to consume the actor-bound package grant. Otherwise relay bytes through separately authenticated source and target clients. Never infer live identity from native database IDs alone, weaken recovery identity checks, or change frozen inputs during retry.
5. **NetworkX has no snapshot mode:** `Store.to_networkx(...)` emits current visible graph records, graph metadata needed to interpret them, and minimum schema/Pattern information required to preserve graph structure. Descriptor ID/name/value/provenance, Pattern records and resource records are current graph data. Descriptor records are visible in each Object's `descriptors` mapping and use the full `kind`, `id`, `namespaceId`, `objectId`, `name`, and `value` shape; record interpretation also requires the Namespace, Object and name to match the graph location. An ordinary scientific mapping with `kind="Descriptor"` remains a value when it does not match that context. Binary bytes remain in explicit providers, never graph attributes. `Store.from_networkx(...)` serializes the graph's actual current nodes, edges, Descriptor records, attributes and included schema. It does not compare to a prior export, restore hidden originals, or carry history. Resource content is supplied through `resources` / `resource_source`; a complete Exchange package is self-contained. Missing identities are allocated once during frozen preparation. Standalone metadata uses `historyMode="disabled"`, `includeHistory=false`, subgraph scope and current Object IDs as roots. NetworkX performs basic shape and endpoint checks; the Server owns graph, schema, Pattern, typed-value, geometry and time semantics before planning or effects. The former `snapshot` graph attribute, `descriptorMetadata` sidecar and equality check have been removed.
6. **Always-lazy import results:** import analysis, apply, plan inspection, recovery and saved outcomes use one lazy result interface at every size. Do not add `result_mode`, legacy readers, or a required whole-result conversion helper. The interface provides scalar metadata and disk-backed/paged mappings and collections for groups, summaries, diagnostics and identity mappings. Iteration and keyed lookup fetch bounded pages. Server result segments and the Python protected result reference remain durable and tied to the exact action/receipt identity. `DepositError` remains the Python action failure surface; when analysis finds conflicts, Server commits an immutable diagnostic result and its receipt, then Python raises `IMPORT_CONFLICT` with `details["conflicts"]` exposed as a lazy collection. The exception retains the owning `ImportResult` so callers can close it after inspecting details. A committed apply cannot be reported as failed because result retrieval is incomplete; preserve the committed receipt/envelope and return `COMMITTED_RESULT_PENDING` for resumption against the same result. Server receipt-owned envelope and result/segment records commit in the same Neo4j transaction as apply; do not store a large outcome JSON property. Server retains them for the receipt lifetime; `action.release` detaches only the prepared session. Python stores the bounded envelope, streams pages into protected segments with exact positions, and persists the local index before confirming action release. On any failure after commit, retain action/envelope and resume the same result. `ImportResult` reads local segments lazily. Completed local results follow the existing 30-day policy, pinned by readers/workflows; closing a result releases its reader, not the Server receipt. Preserve completed local results after Namespace deletion.
7. **History reachability:** Python preserves and integrity-checks the complete original package, including `history.json` and every resource content entry. The Server validates source history/references and, for existing-target import, creates receiving DResources only for resource identities referenced by imported current-state Descriptors. History-only content is not published as an unattached receiving resource. Authorized clone retains history-only resources and remaps their references; clone semantics belong to Stage 6.
8. **No production matching deadline:** remove the current fixed 30-second matching deadline for import matching. Keep cancellation checkpoints and respond to actual disk/memory pressure. Cancellation or resource pressure must fail without returning a partial plan or partially applying domain data. This approval is specific to import matching; unrelated query and recovery time policies remain in force unless separately approved.
9. **No new capacity ceilings:** remove fixed Server resource bytes, Exchange ZIP bytes, expanded archive bytes and entry-count caps, and Python’s 1 GiB protected-storage transfer quota. Do not replace them with larger numeric caps, transfer-duration caps, compression-ratio policy caps, aggregate per-user quotas or hidden concurrent-package limits. Preserve fixed-size chunks/records only when total inputs, mappings, results, indexes and receipts are segmented/paged without total-operation ceilings.

## 2. Public API and result shape

The resource-bearing interfaces are:

```python
Store.export_exchange(*, roots=None, max_hops=None,
                      root_class_boundary=True) -> ExchangeBundle

Store.import_exchange(source, *, rules=None) -> ImportResult
Store.import_from(source_store, *, roots=None, max_hops=None,
                  root_class_boundary=True, rules=None) -> ImportResult

Store.from_dict(data, *, resources=None, resource_source=None,
                rules=None) -> ImportResult
Store.import_subtree(subtree, *, resources=None, resource_source=None,
                     rules=None) -> ImportResult
Store.from_networkx(graph, *, resources=None, resource_source=None,
                     rules=None) -> ImportResult

Store.import_inspect(plan_id) -> ImportResult
Store.import_apply(plan_id) -> ImportResult
```

These exact method names and signatures are the design baseline. `import_inspect` wraps `deposit.get.importPlan`; `import_apply` remains one whole-plan atomic action with no conflict-resolution or group-selection input. Existing subtree/root traversal validation and resource-free call paths remain semantically intact, with their result type changing to `ImportResult`.

`ExchangeBundle` exposes immutable source binding, package identity/reference, manifest, graph and resource-reader access. Metadata/content inspection materializes and integrity-validates ZIP members and bytes in protected storage; it does not claim local Server-domain semantic validation. The Server remains authoritative for that validation before import effects. Bundle readers are context-managed and pin bytes independently of the bundle?s close request until the reader closes. `save(path)` writes a caller-requested portable ZIP; it does not transfer ownership of or mutate the bundle?s protected staging.

`ImportResult` is always-lazy and is backed by one final unversioned Server result contract. Existing procedure names and signatures remain unchanged: `deposit.import.analyze(source, rules, token)`, `deposit.import.apply(planId, token)`, and `deposit.get.importPlan(planId, token)`. Analyze and apply return the immutable `deposit.import-result` envelope: a scalar header plus known collection descriptors only: `resultId`, `operationId`, `kind`, `state`, `namespaceId`, `planId` (nullable), `revision`, `expiresAt`, and `collections`. Each collection descriptor is `{kind: "sequence"|"mapping", count: integer}`; no outcomes or mappings are embedded in the envelope. `get.importPlan` returns an unversioned `{plan, analysisResult}` wrapper with `plan` (the current plan lifecycle observation) and `analysisResult` (the exact saved analysis envelope, unchanged). The plan observation preserves existing lifecycle spelling, such as `ready` and `applied`, and includes `planId`, `namespaceId`, `targetRevision`, and `expiresAt`. This wrapper reads both under the existing plan/Namespace synchronization so its lifecycle and result reference are a consistent observation. `analysisResult.resultId`, `operationId`, `kind`, `state`, `revision`, `expiresAt`, and collection descriptors never change after apply; the inspection wrapper does not relabel the result, null its operation ID, or create a replacement result. `ImportResult` retains the current plan observation separately from the immutable analysis-result `state`. The discovery `capabilities` array advertises semantic capability `pagedImportResults`; Python requires it before import operations. Unsupported result discriminators fail without an eager fallback. The final result contract has no legacy readers or numeric negotiation.

Read-only procedures are `deposit.get.importResult(resultId, token)`, `deposit.get.importResultPage(resultId, collection, cursor, limit, token)`, and `deposit.get.importResultEntry(resultId, collection, key, token)`. A page response returns `resultId`, `collection`, ordered `entries` (sequence values or mapping key/value pairs), and `nextCursor`; it has no separate numeric format marker. A missing mapping key returns `found: false`. Cursors are integrity-bound to the immutable result, collection, and position. Pages and stored segments have bounded units, including a single oversized structured value, so no page or segment requires an unbounded record. Each read enforces receipt actor/scope authorization; possession of a result ID is not authorization.

Every collection value and mapping key uses an explicit descriptor, so a scientific/user mapping cannot be mistaken for a storage reference. `scalar` contains only a bounded primitive (null, Boolean, supported number, or bounded string); every mapping and sequence, even a small one, uses a collection reference. Descriptor forms are `{"type":"scalar","value":...}`, `{"type":"mapping","collection":"...","count":N}`, `{"type":"sequence","collection":"...","count":N}`, or `{"type":"text","collection":"...","bytes":N}`. Mapping collection entries are `{key:<value descriptor>,value:<value descriptor>}`; sequence collection entries are value descriptors. Mapping keys are tagged scalars when bounded and text references when oversized. A text reference points to an ordered sequence whose entries are bounded `{"type":"scalar","value":"..."}` string descriptors; concatenating their strings has exactly the text descriptor's declared UTF-8 byte length. Internal collections are owner-bound to their result, validate declared counts/types/keys and duplicate keys, and are retrieved through the same authorized page/entry procedures. The entry procedure accepts only a bounded plain string key argument; callers enumerate oversized mapping keys through pages instead of sending unbounded keys back for lookup. Python exposes lazy mapping/sequence readers and chunk-readable lazy text; it does not silently construct complete dictionaries, join large text, or otherwise materialize an unbounded value. Plan-wrapper authorization does not itself authorize collection-page reads: a Namespace owner who is not the receipt actor retains plan lifecycle visibility, while each page/entry read remains restricted to the receipt actor and Namespace scope.

`ImportResult` exposes stable operation/action identity, immutable result state, plan ID (when analysis succeeds), target revision, expiry and summary metadata, plus lazy `groups`, `identity_mappings`, `row_mappings`, `conflicts`/diagnostics, and receipt-backed outcome collections where applicable. For plan inspection, the current plan observation is retained separately from the immutable analysis result. Iteration, bounded paging, and keyed lookup read local protected segments; they never load the whole result.

`resources` maps only `resources/<sha256>` content entries to `Path`, bytes, or readable binary streams. Streams are consumed from their current position, at most once per content entry, and remain caller-owned/open. Nonseekable streams are frozen incrementally into protected staging. Explicit content takes precedence over `resource_source`; invalid explicit content is an error and cannot fall back. Verify checksum and byte length for every resource record sharing a content entry. `resource_source` is an authenticated Store bound to the source Namespace/deployment or a checked ExchangeBundle used as a content fallback; IDs never identify receiving resources. A complete checked `ExchangeBundle` is passed as the data argument by itself and supplies its own content readers.

NetworkX graphs carry current graph data, not source export snapshots. Python conversion performs only basic shape checks needed to construct or consume the graph/package and does not duplicate Server scientific/domain validation. The receiving Server validates the reconstructed package before analysis plans or effects. Graph conversion preserves actual supplied values and does not compare them with an earlier export.

### Compatibility and versioning

Changing convenience method results from dictionaries to `ImportResult`, adding `import_exchange`, `import_from`, `export_exchange`, and `import_inspect`, extending graph/dictionary providers, and removing NetworkX snapshot-tracking behavior are public Python contract changes. Update Python API docs and assess the package version impact in its versioned API catalog. Keep the existing `deposit.import.analyze(source, rules, token)`, `deposit.import.apply(planId, token)`, `deposit.get.importPlan(planId, token)`, resource upload/download, action prepare/execute/release and authorization signatures unchanged. The final analyze/apply envelope is `deposit.import-result`; the read-only result procedures use their unversioned names and one strict contract. Python requires semantic capability `pagedImportResults` for import operations. Do not add numeric protocol negotiation, exact Server release equality checks, old aliases, or an eager result fallback. Keep optional NetworkX installation optional.

## 3. Routing, workflow, recovery and ownership

### Direct handoff and relay

The same-server predicate requires a live endpoint binding and deployment identity backed by current configuration/verified connection context plus compatible database identity. A cloned or restored store can share native IDs; those IDs alone never qualify. Validate source export access and receiving analysis access independently. The actor-bound export grant must be consumable by the receiving actor. If evidence or authorization is insufficient, select relay before analysis and use the independently authenticated endpoints. If handoff analysis is uncertain, resolve its original prepared action before considering a separately frozen relay action. Never replace original arguments while recovering an action.

### Workflow record and state transitions

Create discoverable local workflow ownership before source export. Persist state transitions and immutable bindings/arguments before invoking each remote action:

```text
CREATED
  → SOURCE_EXPORT_REQUESTED → SOURCE_REFERENCE_READY
  → SOURCE_STAGING → SOURCE_STAGED
  → ROUTING_DECIDED
  → TARGET_UPLOAD → TARGET_PACKAGE_READY
  → ANALYSIS_REQUESTED → PLAN_READY
  → APPLY_REQUESTED → APPLYING → APPLIED
```

At any remote boundary, transport loss or an ambiguous receipt moves the workflow to `OUTCOME_UNCERTAIN` until the original prepared action is resolved. Explicit terminal states include `CANCELLED`, `FAILED`, `EXPIRED`, and `ABANDONED` (only when no unresolved server action or plan ownership remains). `PLAN_READY` is a hard apply barrier: recovery, resume and cleanup never apply without a durable `APPLY_REQUESTED` transition recorded by explicit caller intent. If the apply reply is lost, recover the exact apply action and exact committed result; never reanalyze or reapply under a new action.

Expose `Client.pending_imports(*, recovery_directory=None) -> Iterator[ImportWorkflow]`, `Client.inspect_import(workflow) -> ImportWorkflowStatus`, `Client.resume_import(workflow, *, target_store, source_store=None) -> ImportWorkflowStatus`, and `Client.abandon_import(workflow, *, target_store=None, source_store=None) -> ImportWorkflowStatus`. The immutable public workflow reference contains only ID, state, creation time, source/target Namespace IDs, and required endpoints; it contains no credentials, keys, arguments, or paths. Status contains the reference, state/phase, optional `ImportResult`, and bounded cleanup/action status. Inspection is local and side-effect free. Resume borrows authenticated supplied Stores; the source is needed only for unfinished source phases and the target must belong to the receiving Client. Preserve `Client.recover` as the single-action recovery path; shared action-resolution internals do not let action recovery advance the workflow.

Persist workflow ID, caller/actor binding, source and target endpoint/deployment/database/Namespace identities, routing decision and evidence, exact frozen rules and action arguments, package reference and digest, source export receipt/grant, protected staging checkpoint, upload receipt/ID and verified chunk offsets, analysis action/plan reference, apply action, result-segment reference, and admission ownership. Do not persist passwords, bearer tokens, recovery keys in public status, or local sensitive paths in public errors/logs. Chunk checkpoints are verified by digest and refer only to the original frozen source. Expired grants/uploads/plans are explicit terminal or new-operation cases, not a successful resume from a fresh export. One workflow lock serializes resume/apply/abandon. Resume stops at `PLAN_READY` unless durable `APPLY_REQUESTED` exists; `Store.import_apply` records that intent before the request. Abandon records `ABANDON_REQUESTED` and returns `ABANDON_PENDING` while any remote outcome or ownership is unresolved; it never performs a domain action to clean up. Preserve uncertain preparation if safe cancel/release cannot be proven. Mark `ABANDONED` only after ownership release is confirmed; active readers may defer local deletion.

Public pending-work inspection is available without credentials, recovery keys or secret paths. Resume reacquires each endpoint independently through authenticated clients and revalidates every identity binding. Recovery action resolution is distinct from workflow continuation. A process/root lock or lease gives one recovery attempt ownership at a time. Preserve unresolved package inputs on cancellation, disk-full, cleanup failure or ambiguous action outcome. Abandonment cannot delete content still protected by a reader, workflow, plan, action receipt, result receipt or history reference. Retain and report attributable cleanup failures.

### Atomicity and result durability

`deposit.import.apply` remains a single atomic domain operation. Staging, resource publication and receipts have explicit ownership and leases. A failed transaction exposes no partial graph or resource references; any published-but-unattached resources remain under safe orphan/lease/collection policy and are reclaimable only when no plan, reader, receipt, workflow or history dependency protects them. Persist the stable result reference and local page index before confirming `action.release`; release detaches only the prepared session and does not remove receipt-owned results. Segment maps and results into bounded protected records and paged Server storage; bind each segment to the action/receipt ID, ordering, checksum and total count. Replay returns that same result reference and data exactly. A missing/corrupt segment leaves the committed action recoverable and signals incomplete retrieval; it does not transform commit success into apply failure.

Python's protected action journal uses a bounded identity-bound root record with a descriptor for one complete `operation` payload: generation, chunk count, encoded byte length, and SHA-256. The operation JSON is streamed into immutable protected 1 MiB chunks named from the exact operation key, deployment identity scope, generation, and chunk index. Persist an authenticated owner record before writing chunks; atomically publish the new root only after every chunk is verified. The root's key, full identity, and state must equal the decoded operation. A replacement writes a new generation while the old one remains authoritative, then reclaims the old generation under the journal index lock; uncertain cleanup retains its owner for retry. Recovery validates exact ordering, lengths and digest, and rejects missing, substituted, trailing, or mismatched payloads. Admission accounts for each encrypted temporary/new-generation write and replacement peak before writing. The 1,024 unresolved-operation limit counts operation roots only; payload size and segment count have no total application cap.

### Stage 6 full-Namespace clone contract

The clone flow is actor-bound and Server-scoped so it works when the receiving Server has no selected or existing Namespace. `Client.clone_namespace(token, source, *, recovery_directory=None) -> CloneResult` accepts a complete Exchange package/provider and returns the created Namespace identity with lazy, receipt-bound mappings. A clone receipt remains Server-scoped after commit; the new Namespace ID is output data, not a retroactive scope change. `Client.recover` resolves the same prepared action and returns a `RecoveredOperation` whose `.result` is the original `CloneResult`, without selecting the cloned Namespace or reconstructing mappings from current graph state. Pending clone work is discoverable locally from protected recovery storage without credentials or sensitive paths; resumption reauthenticates the original actor and receiving deployment/database.

Clone package staging is a private, authenticated Server-scoped upload, bound to actor, deployment/database, action, and immutable package digest. It is not a scientific `DResource` and does not create a hidden Namespace. Upload chunks use existing protected transfer/admission principles, verified offsets, replay-safe action receipts and attributable abort/cleanup. Clone consumption pins the finished package until action and result ownership resolve. Existing Namespace-owned package resources retain their normal source authorization checks.

Clone preserves the package Namespace name. If that name already exists, including a same-server source Namespace, cloning fails atomically with `DUPLICATE`. There is no target-name override, suffixing, or overwrite; historical names remain unchanged. Name uniqueness must be serialized with destination creation so concurrent clones cannot both claim one name. A successful clone atomically creates the Namespace and owner role, remapped current graph/resources, retained history and receipt/result reference. Persistent history includes history-only resources and consistent remapping of epochs, revisions, snapshots, touches, dependencies, tags and reversal/restore links. Source actor identifiers remain historical attribution only and do not create local accounts or roles. Failed clone transactions leave no partially created Namespace; operational staging cleanup remains recoverable.

These clone contracts were approved by the user on 2026-11-11.

Python distribution versions use Git tags as their source of truth through `setuptools-scm`, the sole build-time version resolver. The project release-tag convention is `vX.Y.Z` with optional PEP 440 prerelease suffixes such as `v2.4.0rc1`; the leading `v` is normalized away. A clean `v2.4.0` produces `2.4.0`. Three commits after that tag produce `2.4.1.dev3+g<hash>` under the standard `guess-next-dev` and `node-and-date` schemes. Dirty state adds `.dYYYYMMDD` to the local portion (for example `2.4.1.dev3+g<hash>.d20261111`, or `2.4.1.dev0+g<hash>.d20261111` when dirty at the tag). There is no custom Git-versioning or build-input validation: tagless and shallow checkouts follow setuptools-scm built-in discovery/default behavior, not a project-specific fail-closed rule. Under the tested setuptools-scm 10.3.4 environment, the tagless repository checkout produced `0.1.dev34+g2ad2f7528.d20261111`; this is inferred from the available checkout state, not a fixed fallback. Shallow repositories may continue using available tag/history data. Complete history and release tags are required for reliable release provenance but are not enforced by custom validation. Source distributions preserve the resolved version through setuptools-scm metadata for Git-free wheel rebuilds; the project does not authenticate source-archive origin. Installed runtime reads packaged metadata and never invokes Git. Python package versions are never written into Exchange output; Exchange `depositVersion` remains Server-version provenance or null. The user selected setuptools-scm-only behavior on 2026-11-11.

## 4. Capacity, representation and admission inventory

### Server import transaction estimate

The Server reserves Neo4j database and transaction-log capacity separately before import writes, then grows the reservation in blocks as result rows are emitted. The current planning formula uses UTF-8 serialized properties plus 512 bytes per planned node/index and 256 bytes per planned relationship/index for the database estimate. The transaction-log estimate uses two serialized-image copies plus 128 bytes per planned node or relationship command. It counts generated records, reserves existing properties affected by form-scope deletions before mutation, and accounts for the exact before/after images and journal rows before appending import history. Result records and the receipt allowance use the same transaction-owned reservation. SQLite and JSONL scratch writes reserve each serialized row plus offset/index overhead before writing; each scratch lease releases its commitment after closing and deleting its files. OCFL staging and publication are accounted separately on their resolved physical volume; publishing a resource adds its temporary-copy peak while preserving commitments for later staged resources.

Record/index allowances are estimates for the pinned Neo4j distribution (`2026.05.0`), not guaranteed allocation bounds. The retained calibration fixture wrote 20,000 tiny records, one long UTF-8 value and a large before/after image: the database directory stayed at 868,352 bytes (no page-store growth observed), transaction logs grew by 4,022,495 bytes, and the formula estimated 12,342,576 database bytes and 6,763,360 log bytes. This supports the log estimate for that sample; it does not measure database allocation because the existing store files were preallocated, and it does not establish bounds for other layouts. Page-store growth, transaction command framing, indexes and filesystem allocation can differ from logical property sizes. Admission checks current free space and blocks new work based on those estimates; filesystem exhaustion and transaction rollback remain possible, so the implementation retains published artifacts until receipt/orphan recovery proves ownership. Do not report estimated reservation bytes as measured allocation or as a capacity guarantee.

This is an inventory for implementation and tests, not a claim that every limit below is a transfer ceiling. Remove only approved fixed capacity restrictions; keep format-inherent, authorization, input validation and bounded-page semantics. Every size/count conversion and staging estimate uses checked arithmetic and explicit overflow/representation failure.

## 6. Stage7 scenario, capacity, failure and compatibility matrix

The test harness acceptance map provides row-level ownership and evidence columns. The final phase must cover:

### Scenarios and behavior

- S1 Local Store → remote Store relay; S2 remote A → remote B relay; S3 portable ZIP → local Store; S4 portable ZIP → remote Store; S5 local Namespace A → B on same Server; S6 remote Namespace A → B on same Server; S7 remote Store → local Store; S8 dictionary or NetworkX graph plus resource providers → local/remote Store.
- Resource-free, zero-byte, multiple resource, repeated reference, distinct identities with identical content, edited files after preparation, geometry, nested scientific values, Classes, Patterns, relationships, memberships and User Tools as applicable.
- Persistent whole-Namespace owner success and non-owner rejection; complete source history and history-only resources validated, with no history-only receiving DResource on existing-target import; Stage6 clone retains the history-only closure when authorized.
- Same-server eligible actor with usable package grant avoids client download. Different actor, missing grant, endpoint alias or uncertain/colliding deployment identity relays under independently authenticated sessions or fails safely.
- NetworkX output contains only graph-visible current data plus necessary schema/Pattern context: no snapshot/cache/history attribute and no hidden original restoration. Import reflects actual edited graph state and rejects resource references without verified content providers.
- Recovery for ambiguous source export, download, upload, analysis and apply; Server restart; client termination; exact large-result replay; `PLAN_READY` never crosses to apply without durable explicit intent.

### Actual capacity and scalable processing

- Real resource larger than 2 GiB; Exchange ZIP larger than 2 GiB; expanded Exchange content larger than 2 GiB; ZIP64 archive beyond 4 GiB; more than 65,535 and more than 100,000 entries.
- Protected staging over 1 GiB with no aggregate quota; competing import/export/upload/maintenance admission; disk exhaustion after initial admission; throttling/queue behavior, rollback and safe published-resource retention.
- Actual identity mapping and/or receipt larger than 16 MiB, retrieved completely and replayed exactly. Import applies atomically and exercises Server matching, materialization, Neo4j mutation, result persistence and replay; package upload alone is not sufficient.
- Streaming JSON/history, high-entry indexes, large candidate/conflict sets, disk-backed plan summaries/results, checked overflow and `2^53−1` format boundary failures without allocating theoretical maxima. Matching cancellation/resource pressure returns no partial plan. Record observed Neo4j transaction/rollback and runtime constraints.

### Failure, security and compatibility

- Disk-full, memory pressure, cancellation at every write boundary, checksum mismatch, corrupt/missing protected chunks, corrupt CRC, unsafe/duplicate entries, malformed schema/reference, changed endpoint/actor/Namespace/deployment, revoked authorization, expired grant/upload/plan, concurrent resume, bundle closure during workflow and attributable cleanup failure.
- Verify no resource can be reclaimed while protected by a receipt, plan, reader, workflow or history. Preserve authentication, actor-bound grants, source/target permissions, package integrity and atomic apply.
- Declared Windows, Python, Neo4j driver and NetworkX combinations; NetworkX-absent package checks; wheel/sdist verification against exact supported Server builds. Since results and NetworkX behavior are public API changes, tests assert new `ImportResult` across resource-free and large cases and reject embedded NetworkX snapshots, alongside any explicitly retained stable APIs.
- Use the established runtime and protected storage for actual boundaries. Simulated remote endpoints/transport fixtures prove protocol behavior, but are labeled as simulated, not as observed inter-host deployment. Record commands, runtime/server builds, artifacts, exact sizes/counts, memory/disk observations, executed/reused/skipped/unexecuted criteria and retained evidence. Do not claim unlimited capacity.
