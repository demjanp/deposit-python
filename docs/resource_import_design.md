# Resource-bearing imports and capacity design

**Status:** Stage 1 design; independent architect consistency review passed with no blocking findings. This document records the approved Stage 1 interface decisions and implementation contract for later stages; it does not claim product implementation.

**Scope:** resource-bearing Exchange packages imported into existing Namespaces, portable package handling, graph providers, recovery, capacity and test ownership. Full-Namespace clone is included in the sequential Stage 6 implementation; its detailed contract is completed there before that stage’s implementation. Stages 1–6 execute sequentially; Stage 7 is the only full acceptance phase.

## 1. Approved interface decisions

1. **One immutable package pipeline:** select source → freeze a complete Exchange package → analyze against the target → explicit apply. Analysis never applies changes.
2. **Lazy Exchange bundles:** `Store.export_exchange(...)` returns a context-managed `ExchangeBundle`. It may initially hold a remote package reference containing source binding, resource ID, length and checksum, without claiming the manifest or graph were inspected locally. Accessing manifest/graph/resource content, saving a portable ZIP, or converting to a graph materializes and validates the complete package in protected storage. `Store.import_from(...)` may pass the eligible remote reference directly to the target without downloading through the client.
3. **Bundle ownership:** caller-owned streams and Stores are borrowed and remain open. The bundle owns only its local protected staging. Closing a bundle releases owned staging only when no reader/workflow owns it; readers and submitted workflows pin the immutable bytes they use. Saving a portable ZIP is a separate, explicit output operation with caller-selected destination ownership. Never substitute an ordinary plaintext temporary ZIP for protected staging.
4. **Conservative routing:** direct handoff is allowed only when live endpoint/deployment provenance and database identity are sufficiently certain and the receiving actor is authorized to consume the actor-bound package grant. Otherwise relay bytes through separately authenticated source and target clients. Never infer live identity from native database IDs alone, weaken recovery identity checks, or change frozen inputs during retry.
5. **NetworkX has no snapshot mode:** remove snapshot metadata, export snapshots, history caches, and all snapshot equality/change tracking from NetworkX export/import. `Store.to_networkx(...)` emits current visible graph records, graph metadata needed to interpret them, and minimum schema/pattern information required to preserve graph semantics. Descriptor ID/name/value/provenance, Pattern records and resource records are actual current data and must remain represented. `Store.from_networkx(...)` serializes the graph’s actual current nodes, edges, Descriptor records, attributes and required schema; it does not compare to a prior export, restore hidden originals, or carry history. Preserve resource values only through explicit `resources` / `resource_source` inputs; never embed binary bytes in graph attributes. The frozen preparation step allocates any missing identities exactly once. The standalone package metadata uses a valid current Exchange representation (`historyMode="disabled"`, `includeHistory=false`, and consistent scope/root fields); it does not use an invented `historyMode="none"`. Current implementation uses `_METADATA_KEY = "snapshot"`, stores the full snapshot in `graph.graph`, and rejects graph edits by comparison; Stage 4 removes this behavior rather than adding an option.
6. **Always-lazy import results:** import analysis, apply, plan inspection, recovery and saved outcomes use one lazy result interface at every size. Do not add `result_mode`, a legacy dictionary result, or a required whole-result conversion helper. The interface provides scalar metadata and disk-backed/paged mappings and collections for groups, summaries, diagnostics and identity mappings. Iteration and keyed lookup fetch bounded pages. Server result segments and the Python protected result reference remain durable and tied to the exact action/receipt identity. `DepositError` remains the action failure surface; large structured diagnostics use the same lazy collection abstraction. A committed apply cannot be reported as failed because result retrieval is incomplete; preserve the committed receipt/envelope and return `COMMITTED_RESULT_PENDING` for resumption against the same result. Server receipt-owned envelope and result/segment records commit in the same Neo4j transaction as apply; do not store a large outcome JSON property. Server retains them for the receipt lifetime; `action.release` detaches only the prepared session. Python stores the bounded envelope, streams pages into protected segments with exact positions, and persists the local index before confirming action release. On any failure after commit, retain action/envelope and resume the same result. `ImportResult` reads local segments lazily. Completed local results follow the existing 30-day policy, pinned by readers/workflows; closing a result releases its reader, not the Server receipt. Preserve completed local results after Namespace deletion. Diagnostics use the same collection references after a failed transaction rolls back; pressure failure retains only bounded error code/state.
7. **History reachability:** an existing-target import validates and preserves the complete original package, including `history.json` and resources reachable only from history, but creates receiving DResources only for resource identities referenced by imported current-state Descriptors. The history-only content is not published as an unattached receiving resource. When clone is authorized, it must retain history-only resources and their remapped references; detailed clone design belongs to Stage 6.
8. **No production matching deadline:** remove the current fixed 30-second matching deadline for import matching. Keep cancellation checkpoints and respond to actual disk/memory pressure. Cancellation or resource pressure must fail without returning a partial plan or partially applying domain data. This approval is specific to import matching; unrelated query and recovery time policies remain in force unless separately approved.
9. **No new capacity ceilings:** remove fixed Server resource bytes, Exchange ZIP bytes, expanded archive bytes and entry-count caps, and Python’s 1 GiB protected-storage transfer quota. Do not replace them with larger numeric caps, transfer-duration caps, compression-ratio policy caps, aggregate per-user quotas or hidden concurrent-package limits. Preserve fixed-size chunks/records only when total inputs, mappings, results, indexes and receipts are segmented/paged without total-operation ceilings.

## 2. Public API and result shape

The resource-bearing interfaces are:

```python
Store.export_exchange(*, roots=None, max_hops=None,
                      root_class_boundary=True) -> ExchangeBundle

Store.import_exchange(source, *, rules=None) -> ImportResult
Store.import_from(source_store, *, roots=None, max_hops=None,
                  root_class_boundary=True, rules=None) -> ImportResult

Store.from_dict(data, *, resources=None, resource_source=None,
                rules=None) -> ImportResult
Store.import_subtree(subtree, *, resources=None, resource_source=None,
                     rules=None) -> ImportResult
Store.from_networkx(graph, *, resources=None, resource_source=None,
                     rules=None) -> ImportResult

Store.import_inspect(plan_id) -> ImportResult
Store.import_apply(plan_id) -> ImportResult
```

These exact method names and signatures are the design baseline. `import_inspect` wraps `deposit.get.importPlan`; `import_apply` remains one whole-plan atomic action with no conflict-resolution or group-selection input. Existing subtree/root traversal validation and resource-free call paths remain semantically intact, with their result type changing to `ImportResult`.

`ExchangeBundle` exposes immutable `source_binding`, package identity/reference, `manifest`, `graph`, and resource-reader access. Metadata/content inspection causes remote materialization and complete validation. Bundle readers are context-managed and pin bytes independently of the bundle’s close request until the reader closes. `save(path)` writes a caller-requested portable ZIP; it does not transfer ownership of or mutate the bundle’s protected staging.

`ImportResult` is always-lazy and is backed by an explicitly versioned Server result protocol. Existing procedure names and signatures remain unchanged: `deposit.import.analyze(source, rules, token)`, `deposit.import.apply(planId, token)`, and `deposit.get.importPlan(planId, token)`. Analyze and apply return the immutable `deposit.import-result/1` envelope: a scalar header plus known collection descriptors only: `resultId`, `operationId`, `kind`, `state`, `namespaceId`, `planId` (nullable), `revision`, `expiresAt`, and `collections`. Each collection descriptor is `{kind: "sequence"|"mapping", count: integer}`; no outcomes or mappings are embedded in the envelope. `get.importPlan` returns a versioned `deposit.import-plan/1` wrapper with `plan` (the current plan lifecycle observation) and `analysisResult` (the exact saved analysis envelope, unchanged). The plan observation preserves existing lifecycle spelling, such as `ready` and `applied`, and includes `planId`, `namespaceId`, `targetRevision`, and `expiresAt`. This wrapper reads both under the existing plan/Namespace synchronization so its lifecycle and result reference are a consistent observation. `analysisResult.resultId`, `operationId`, `kind`, `state`, `revision`, `expiresAt`, and collection descriptors never change after apply; the inspection wrapper does not relabel the result, null its operation ID, or create a replacement result. `ImportResult` retains the current plan observation separately from the immutable analysis-result `state`. Discovery advertises `importResultFormats: [1]`; Python requires this capability/build gate before mutation and plan inspection. Unsupported formats fail without an eager fallback. Existing saved journal formats remain readable, and each new record identifies its result format. The plan-inspection wrapper uses the same V1 result capability gate.

Read-only V1 procedures are `deposit.get.importResultV1(resultId, token)`, `deposit.get.importResultPageV1(resultId, collection, cursor, limit, token)`, and `deposit.get.importResultEntryV1(resultId, collection, key, token)`. A page response uses `format="deposit.import-result-page/1"` and returns `resultId`, `collection`, ordered `entries` (sequence values or mapping key/value pairs), and `nextCursor`. A missing mapping key returns `found: false`. Cursors are integrity-bound to the immutable result, collection, and position. Pages and stored segments have bounded units, including a single oversized structured value, so no page or segment requires an unbounded record. Each read enforces receipt actor/scope authorization; possession of a result ID is not authorization.

Every collection value and mapping key uses an explicit descriptor, so a scientific/user mapping cannot be mistaken for a storage reference. `scalar` contains only a bounded primitive (null, Boolean, supported number, or bounded string); every mapping and sequence, even a small one, uses a collection reference. Descriptor forms are `{"type":"scalar","value":...}`, `{"type":"mapping","collection":"...","count":N}`, `{"type":"sequence","collection":"...","count":N}`, or `{"type":"text","collection":"...","bytes":N}`. Mapping collection entries are `{key:<value descriptor>,value:<value descriptor>}`; sequence collection entries are value descriptors. Mapping keys are tagged scalars when bounded and text references when oversized. A text reference points to an ordered sequence whose entries are bounded `{"type":"scalar","value":"..."}` string descriptors; concatenating their strings has exactly the text descriptor's declared UTF-8 byte length. Internal collections are owner-bound to their result, validate declared counts/types/keys and duplicate keys, and are retrieved through the same authorized V1 page/entry procedures. The entry procedure accepts only a bounded plain string key argument; callers enumerate oversized mapping keys through pages instead of sending unbounded keys back for lookup. Python exposes lazy mapping/sequence readers and chunk-readable lazy text; it does not silently construct complete dictionaries, join large text, or otherwise materialize an unbounded value. Plan-wrapper authorization does not itself authorize collection-page reads: a Namespace owner who is not the receipt actor retains plan lifecycle visibility, while each V1 read remains restricted to the receipt actor and Namespace scope.

`ImportResult` exposes stable operation/action identity, immutable result state, plan ID (when analysis succeeds), target revision, expiry and summary metadata, plus lazy `groups`, `identity_mappings`, `row_mappings`, `conflicts`/diagnostics, and receipt-backed outcome collections where applicable. For plan inspection, the current plan observation is retained separately from the immutable analysis result. Iteration, bounded paging, and keyed lookup read local protected segments; they never load the whole result.

`resources` maps `resources/<sha256>` package paths to `Path`, bytes, or readable binary streams. Streams are consumed from their current position, at most once per provider, and remain caller-owned/open. Nonseekable streams are frozen incrementally into protected staging. Explicit content takes precedence over `resource_source`; invalid explicit content is an error and cannot fall back. Verify checksum and byte length for every resource record sharing a content entry. Resolve IDs only through typed `DResource` references and a source Store bound to the declared Namespace/deployment; IDs never identify receiving resources.

NetworkX graphs carry current graph data, not source export snapshots. Graph conversion preserves MultiDiGraph node/edge identity, Descriptor identity and provenance, record kinds, graph-visible schema, Patterns, and typed resource references needed for reconstruction. It rejects unsupported/missing schema or references and never compares the graph with an earlier export. Source Namespace identity may be carried as provenance needed to bind typed resource references; export revision, manifest baseline, snapshot object, history or original-value cache is not carried. Reconstruct the standalone current-state package with the Exchange-valid disabled history mode and internally consistent roots/scope. It does not round-trip history. Whole-Namespace persistent source export still follows Server owner authorization; converting that export to a graph does not authorize lossless history backup or make the graph a complete package.

### Compatibility and versioning

Changing convenience method results from dictionaries to `ImportResult`, adding `import_exchange`, `import_from`, `export_exchange`, and `import_inspect`, extending graph/dictionary providers, and removing NetworkX snapshot-tracking behavior are public Python contract changes. Update Python API docs and assess the package version impact in its versioned API catalog. Keep the existing `deposit.import.analyze(source, rules, token)`, `deposit.import.apply(planId, token)`, `deposit.get.importPlan(planId, token)`, resource upload/download, action prepare/execute/release and authorization signatures unchanged. The existing analyze/apply response envelope is explicitly versioned as `deposit.import-result/1`; add the read-only V1 envelope/page/entry procedures above as versioned catalog entries. Python requires discovery capability `importResultFormats: [1]` and the exact Server build gate before mutation. Never silently change an unversioned wire shape or use an eager legacy-result fallback. Keep optional NetworkX installation optional.

## 3. Routing, workflow, recovery and ownership

### Direct handoff and relay

The same-server predicate requires a live endpoint binding and deployment identity backed by current configuration/verified connection context plus compatible database identity. A cloned or restored store can share native IDs; those IDs alone never qualify. Validate source export access and receiving analysis access independently. The actor-bound export grant must be consumable by the receiving actor. If evidence or authorization is insufficient, select relay before analysis and use the independently authenticated endpoints. If handoff analysis is uncertain, resolve its original prepared action before considering a separately frozen relay action. Never replace original arguments while recovering an action.

### Workflow record and state transitions

Create discoverable local workflow ownership before source export. Persist state transitions and immutable bindings/arguments before invoking each remote action:

```text
CREATED
  → SOURCE_EXPORT_REQUESTED → SOURCE_REFERENCE_READY
  → SOURCE_STAGING → SOURCE_STAGED
  → ROUTING_DECIDED
  → TARGET_UPLOAD → TARGET_PACKAGE_READY
  → ANALYSIS_REQUESTED → PLAN_READY
  → APPLY_REQUESTED → APPLYING → APPLIED
```

At any remote boundary, transport loss or an ambiguous receipt moves the workflow to `OUTCOME_UNCERTAIN` until the original prepared action is resolved. Explicit terminal states include `CANCELLED`, `FAILED`, `EXPIRED`, and `ABANDONED` (only when no unresolved server action or plan ownership remains). `PLAN_READY` is a hard apply barrier: recovery, resume and cleanup never apply without a durable `APPLY_REQUESTED` transition recorded by explicit caller intent. If the apply reply is lost, recover the exact apply action and exact committed result; never reanalyze or reapply under a new action.

Expose `Client.pending_imports(*, recovery_directory=None) -> Iterator[ImportWorkflow]`, `Client.inspect_import(workflow) -> ImportWorkflowStatus`, `Client.resume_import(workflow, *, target_store, source_store=None) -> ImportWorkflowStatus`, and `Client.abandon_import(workflow, *, target_store=None, source_store=None) -> ImportWorkflowStatus`. The immutable public workflow reference contains only ID, state, creation time, source/target Namespace IDs, and required endpoints; it contains no credentials, keys, arguments, or paths. Status contains the reference, state/phase, optional `ImportResult`, and bounded cleanup/action status. Inspection is local and side-effect free. Resume borrows authenticated supplied Stores; the source is needed only for unfinished source phases and the target must belong to the receiving Client. Preserve `Client.recover` as the single-action recovery path; shared action-resolution internals do not let action recovery advance the workflow.

Persist workflow ID, caller/actor binding, source and target endpoint/deployment/database/Namespace identities, routing decision and evidence, exact frozen rules and action arguments, package reference and digest, source export receipt/grant, protected staging checkpoint, upload receipt/ID and verified chunk offsets, analysis action/plan reference, apply action, result-segment reference, and admission ownership. Do not persist passwords, bearer tokens, recovery keys in public status, or local sensitive paths in public errors/logs. Chunk checkpoints are verified by digest and refer only to the original frozen source. Expired grants/uploads/plans are explicit terminal or new-operation cases, not a successful resume from a fresh export. One workflow lock serializes resume/apply/abandon. Resume stops at `PLAN_READY` unless durable `APPLY_REQUESTED` exists; `Store.import_apply` records that intent before the request. Abandon records `ABANDON_REQUESTED` and returns `ABANDON_PENDING` while any remote outcome or ownership is unresolved; it never performs a domain action to clean up. Preserve uncertain preparation if safe cancel/release cannot be proven. Mark `ABANDONED` only after ownership release is confirmed; active readers may defer local deletion.

Public pending-work inspection is available without credentials, recovery keys or secret paths. Resume reacquires each endpoint independently through authenticated clients and revalidates every identity binding. Recovery action resolution is distinct from workflow continuation. A process/root lock or lease gives one recovery attempt ownership at a time. Preserve unresolved package inputs on cancellation, disk-full, cleanup failure or ambiguous action outcome. Abandonment cannot delete content still protected by a reader, workflow, plan, action receipt, result receipt or history reference. Retain and report attributable cleanup failures.

### Atomicity and result durability

`deposit.import.apply` remains a single atomic domain operation. Staging, resource publication and receipts have explicit ownership and leases. A failed transaction exposes no partial graph or resource references; any published-but-unattached resources remain under safe orphan/lease/collection policy and are reclaimable only when no plan, reader, receipt, workflow or history dependency protects them. Persist the stable result reference and local page index before confirming `action.release`; release detaches only the prepared session and does not remove receipt-owned results. Segment maps and results into bounded protected records and paged Server storage; bind each segment to the action/receipt ID, ordering, checksum and total count. Replay returns that same result reference and data exactly. A missing/corrupt segment leaves the committed action recoverable and signals incomplete retrieval; it does not transform commit success into apply failure.

No implementation stage runs a full Server suite, full Python suite, broad regression/acceptance matrix, declared version matrix or install artifact matrix. Each stage runs only focused checks for its changes and directly affected dependencies. Cross-stage temporary incompleteness is tracked. Stage 7 alone runs the comprehensive final gates after authorized Stage1–6 work is complete.

## 6. Stage7 scenario, capacity, failure and compatibility matrix

The test harness acceptance map provides row-level ownership and evidence columns. The final phase must cover:

### Scenarios and behavior

- S1 Local Store → remote Store relay; S2 remote A → remote B relay; S3 portable ZIP → local Store; S4 portable ZIP → remote Store; S5 local Namespace A → B on same Server; S6 remote Namespace A → B on same Server; S7 remote Store → local Store; S8 dictionary or NetworkX graph plus resource providers → local/remote Store.
- Resource-free, zero-byte, multiple resource, repeated reference, distinct identities with identical content, edited files after preparation, geometry, nested scientific values, Classes, Patterns, relationships, memberships and User Tools as applicable.
- Persistent whole-Namespace owner success and non-owner rejection; complete source history and history-only resources validated, with no history-only receiving DResource on existing-target import; Stage6 clone retains the history-only closure when authorized.
- Same-server eligible actor with usable package grant avoids client download. Different actor, missing grant, endpoint alias or uncertain/colliding deployment identity relays under independently authenticated sessions or fails safely.
- NetworkX output contains only graph-visible current data plus necessary schema/Pattern context: no snapshot/cache/history attribute and no hidden original restoration. Import reflects actual edited graph state and rejects resource references without verified content providers.
- Recovery for ambiguous source export, download, upload, analysis and apply; Server restart; client termination; exact large-result replay; `PLAN_READY` never crosses to apply without durable explicit intent.

### Actual capacity and scalable processing

- Real resource larger than 2 GiB; Exchange ZIP larger than 2 GiB; expanded Exchange content larger than 2 GiB; ZIP64 archive beyond 4 GiB; more than 65,535 and more than 100,000 entries.
- Protected staging over 1 GiB with no aggregate quota; competing import/export/upload/maintenance admission; disk exhaustion after initial admission; throttling/queue behavior, rollback and safe published-resource retention.
- Actual identity mapping and/or receipt larger than 16 MiB, retrieved completely and replayed exactly. Import applies atomically and exercises Server matching, materialization, Neo4j mutation, result persistence and replay; package upload alone is not sufficient.
- Streaming JSON/history, high-entry indexes, large candidate/conflict sets, disk-backed plan summaries/results, checked overflow and `2^53−1` format boundary failures without allocating theoretical maxima. Matching cancellation/resource pressure returns no partial plan. Record observed Neo4j transaction/rollback and runtime constraints.

### Failure, security and compatibility

- Disk-full, memory pressure, cancellation at every write boundary, checksum mismatch, corrupt/missing protected chunks, corrupt CRC, unsafe/duplicate entries, malformed schema/reference, changed endpoint/actor/Namespace/deployment, revoked authorization, expired grant/upload/plan, concurrent resume, bundle closure during workflow and attributable cleanup failure.
- Verify no resource can be reclaimed while protected by a receipt, plan, reader, workflow or history. Preserve authentication, actor-bound grants, source/target permissions, package integrity and atomic apply.
- Declared Windows, Python, Neo4j driver and NetworkX combinations; NetworkX-absent package checks; wheel/sdist verification against exact supported Server builds.
